## 三、关键踩坑与经验（重要，后续复用）

1. **Windows 公司电脑无管理员权限，软件安装受限**
   - winget 走 python.org 安装器报 `0x80070005`（拒绝访问）；走 Microsoft Store 报 `0x803fb015`（商店不可用）。
   - 解决：改用**免安装便携版**——Python 官方 embeddable zip + `get-pip.py` 引导 pip；ffmpeg 用 gyan.dev essentials zip；Node 用官方 win-x64 zip。解压即用，无需管理员。

2. **Python embeddable 的两个坑**
   - 默认 `pythonXXX._pth` 禁用 site-packages：需取消注释 `import site` 并追加 `Lib\site-packages`，否则 pip 装的包无法 import。
   - 默认不把当前目录加入 `sys.path`：用 `uvicorn ... --app-dir <backend>` 启动，否则 `import main` 失败。

3. **让 yt-dlp 找到便携版 ffmpeg**：通过环境变量 `FFMPEG_LOCATION` 指向 ffmpeg 的 bin 目录，后端在下载选项里透传 `ffmpeg_location`，避免依赖系统 PATH。

4. **YouTube 反爬**：数据中心 / 公司网络访问 YouTube 常触发 “Sign in to confirm you're not a bot”，需 cookies。测试改用无需登录的公开直链（如 w3schools 的 mov_bbb.mp4）。后续若要稳定支持 YouTube，应支持传入 cookies（`--cookies-from-browser` / cookies 文件）。

5. **PowerShell 控制台中文显示乱码**：API 返回的是正确 UTF-8，乱码只是终端编码呈现问题，浏览器正常，不必修改代码。

6. **Windows 沙箱限制**：本机 shell 在默认沙箱下不支持文件系统写隔离，需以无沙箱模式执行写操作类命令。

## 四点六、迭代记录：YouTube PO Token（绕过 bot 校验，免 cookie）

背景：YouTube 对被标记 IP 弹出 `Sign in to confirm you're not a bot`。调研结论——**公开视频的 bot 校验是 IP 信誉问题，不需要用户登录**，强制用户提供 cookies 体验差且不必要。

方案权重评分（用户透明度 0.3 / 成本 0.25 / 稳定性 0.25 / 复杂度 0.2）：

| 方案 | 透明 | 成本 | 稳定 | 复杂 | 加权 |
| --- | --- | --- | --- | --- | --- |
| A PO Token Provider（bgutil）+ player_client 调优 | 5 | 5 | 4 | 3 | **4.40** |
| B 住宅代理 IP 池 | 4 | 2 | 5 | 5 | 4.10 |

结论：**先上 A**（自托管、免费、对用户透明），B 留作大规模/重度封禁时的叠加项。

落地步骤：
1. 升级 `yt-dlp` 2025.01.26 → 2026.06.09（插件框架要求 ≥ 2025.05.22）。
2. `pip install bgutil-ytdlp-pot-provider`（1.3.1），yt-dlp 自动加载。
3. 下载源码 tag 1.3.1（本机无 git，改用 GitHub release zip）→ `pot-provider/server` 执行 `npm ci` + `npx tsc`（`canvas` 用预编译二进制，未踩编译坑）→ `node build/main.js` 起 4416。
4. 后端新增 `_apply_pot_provider()`（`POT_PROVIDER_BASE_URL` / `YT_PLAYER_CLIENTS` 可配，默认零配置）；新增根目录 `start-pot-provider.ps1` 一键拉起 sidecar。

测试结论（真实运行，全程无 cookie）：
- `GET /ping` → 200 `{"version":"1.3.1"}`；yt-dlp verbose 显示 `PO Token Providers: bgutil:http-1.3.1 (external)`。
- CLI 解析 `dQw4w9WgXcQ`：标题/时长正常，**不再出现 bot 校验**；CLI 下载 worst 画质成功。
- 后端 `/api/info`：返回 13 种清晰度（最高 2160p）；`/api/download`（360p）：`queued→downloading→processing→finished`，ffmpeg 合并出 `potcheck.mp4`。

经验沉淀：
- **bot 校验 ≠ 需要登录**：公开内容优先 PO Token，别一上来就逼用户交 cookies。
- 本机无 `git` 时，GitHub 源码可用 `archive/refs/tags/<tag>.zip` + `Expand-Archive` 替代。

- 插件与 provider 服务**版本需一致**（均 1.3.1）。
- PO Token 仅提升可信度、不保证 100% 绕过；重度封禁 IP 仍需代理（方案 B）。

## 四点八、迭代记录：Edge/Chrome cookie 不可直读 → cookies.txt 自动加载

问题：用户用 Edge，下载需登录的视频（如 `rs9Ko4zozqc`）时，无论勾不勾选都失败：勾选→`Could not copy cookie database`；兜底免 cookie→`Sign in to confirm you're not a bot`。对照测试同网络 `dQw4w9WgXcQ` 正常，确认是**该视频需登录** + **Edge cookie 读不出**双重因素。

调研结论（yt-dlp #7271 / #10927 / #15401）：**Chrome/Edge 127+ 应用绑定加密(v20) + 数据库锁库，Windows 下 `--cookies-from-browser` 基本不可用，官方无修复计划**，甚至考虑移除该功能。唯一可靠路径：扩展导出 `cookies.txt` 走 `cookiefile`。

方案权重评分（可靠性 0.4 / 易用 0.35 / 成本 0.25）：

| 方案 | 可靠 | 易用 | 成本 | 加权 |
| --- | --- | --- | --- | --- |
| ① cookies.txt 自动加载（backend/cookies.txt） | 5 | 4 | 4 | **4.45** |
| ② 强制改用 Firefox 读取 | 3 | 2 | 5 | 3.15 |
| ③ ChromeCookieUnlock 插件 / 关 Edge | 2 | 2 | 3 | 2.25 |

结论：**① 为主**（Firefox 仍保留为可选）。

改动：
- 后端 `downloader.py`：新增 `_resolve_cookies_file()`（`COOKIES_FILE` 环境变量优先，否则自动探测 `backend/cookies.txt`）；`_apply_cookies` 调整优先级为 **cookies 文件 > 浏览器读取**。配合既有兜底：浏览器读取失败时退回到「无 browser」，此时若存在 cookies.txt 会被自动采用。
- `.gitignore`：忽略 `backend/cookies.txt` / `cookies.txt`（含敏感登录态）。
- 前端 `HeroSection.vue`：提示文案改为指导 Edge/Chrome 用户用扩展导出 cookies.txt 放到 `backend/cookies.txt`。
- `README.md`：cookies 章节重写，cookies.txt 列为 Edge/Chrome 首选。

测试结论：后端 `ast.parse` 通过；前端 `npm run build` 通过（71 模块）；后端重启加载新逻辑。`cookies.txt` 端到端待用户导出真实文件后验证。

经验沉淀：
- **平台底层限制要尽早查官方 issue**：Edge/Chrome 在 Windows 直读 cookie 是死路，别在「关浏览器/改注册表」上耗时间，直接走 cookies.txt。
- 把「最可靠的方式」设为默认优先级 + 零配置（丢文件即生效），比让用户记环境变量体验好得多。
- 「需要登录的视频」与「IP 被标记」是两类问题：前者必须 cookie，后者靠 PO Token；诊断时用「同网络换个普通视频」快速二分。

## 四点九、迭代记录：免登录最大化(D) + UI 公开优先(C)

背景：cookies.txt 对普通用户体验差。结论——**公开内容应零摩擦，登录内容才需登录态，二者在产品上分层**。方向评估（用户体验 0.35 / 覆盖 0.25 / 成本 0.2 / 分发 0.2）：扩展伴侣(A)4.0、就地优化(D)4.08、UI 重定位(C)3.98、桌面端(B)3.65。先做**性价比最高的 D+C**（A 留作登录内容硬需求时再上）。

### D · 免登录最大化（后端）
- `downloader.py` 新增失败重试链 `_recover` / `_recover_attempts`：
  - cookie 读取失败 → 退回「无浏览器」（有 cookies.txt 仍自动用）。
  - bot 校验 / 年龄门（`not a bot` / `confirm your age` 等）→ 尝试嵌入式客户端 `tv_embedded, web_embedded, default, mweb`，部分受限内容可免登录取到 player 响应。
  - `_apply_player_clients()` 支持单次重试覆盖 `player_client`。
- 新增 `classify_error()`：把 yt-dlp 原始报错归类为 `needs_login / login_or_ip / geo_blocked / unavailable / generic`，返回 `{code, message}` 友好提示。

### C · UI 公开优先（前端）
- `HeroSection.vue`：cookie 控件**默认收起**，仅留一行不显眼的「需要下载会员 / 登录内容？」。报错码为 `needs_login / login_or_ip` 时，显示琥珀色引导卡并**自动展开**登录面板。
- `api.js`：`toError()` 兼容结构化错误，把 `code` 挂到 Error 上；`App.vue` 记录 `parseErrorCode` 透传给 Hero。
- 接口：`/api/info` 错误体改为 `{detail:{code,message}}`；`/api/progress` 增加 `error_code`；`tasks.py` 任务表增 `error_code` 字段。

测试结论（真实运行）：
- 公开视频 `dQw4w9WgXcQ`：正常返回 13 种清晰度。
- 受限视频 `rs9Ko4zozqc`：经嵌入式客户端重试仍失败 → 返回 `{code:"login_or_ip", message:"解析受限…"}`，前端将弹琥珀卡引导。
- 前端 `npm run build` 通过（71 模块）；后端 `ast.parse` 通过。

经验沉淀：
- **内容分层**是这类下载工具的核心产品决策：公开=零摩擦（PO Token + 嵌入式客户端），登录=按需引导，别用同一套 UI 一刀切。
- 失败要给**结构化、可分类**的错误，前端才能"在对的时机做对的引导"，而不是甩一句原始报错。
- 年龄门/bot 的嵌入式客户端绕过是"尽力而为"，会增加失败路径的耗时（实测 ~14s），仅在首次失败后触发，可接受。

## 四点十、迭代记录：抖音网络层修复 + 错误引导

背景：YouTube 已可下载；抖音链接 `modal_id=...` 解析报 `[SSL: UNEXPECTED_EOF_WHILE_READING]`。根因分析：
- **YouTube 需走代理**（`HTTP_PROXY=127.0.0.1:10808`），**抖音必须直连国内**。
- 原 `urllib.urlopen` 会继承系统代理，把抖音流量送到海外节点 → SSL 握手失败。
- 即便强制直连，公司网络仍可能对 `iesdouyin.com` 做连接重置（`10054`）。

方案对比：
| 方案 | 说明 | 评分 |
|------|------|------|
| A. 换 httpx/requests + 抖音直连 | 忽略代理、友好报错 | **8.5** |
| B. 回退 yt-dlp Douyin 提取器 | 同样受网络/签名限制 | 4.0 |

采用 **A**：`douyin.py` 用 `requests.Session(trust_env=False)` + `proxies=None` 强制直连；新增 `classify_douyin_network_error()` 与 `douyin_network` 错误码。

用户侧操作（本机实测仍失败时）：
1. Clash 规则：`douyin.com` / `iesdouyin.com` → **DIRECT**
2. 公司网屏蔽抖音 → **手机热点**或家庭网络
3. 重启后端加载新代码：`uvicorn main:app --reload`

经验沉淀：
- **国内外站点代理策略要分流**：YouTube 走代理、抖音直连，不能全局一刀切。
- SSL EOF 与 Connection Reset 对抖音是不同病因（前者多因错走代理，后者多因防火墙），要分开提示。

## 四点十一、迭代记录：抖音 UA 反爬 + 失效视频识别

背景：换网络后 SSL 通了，但报「分享页未找到 _ROUTER_DATA」。根因：
- 桌面 UA 访问 `iesdouyin.com/share/video/{id}` 会被 **302 到 douyin.com/video** 并返回 JS 反爬页（`_$jsvmprt`），无 `_ROUTER_DATA`。
- **移动端 UA** 留在分享页，可正常拿到 `_ROUTER_DATA`。
- 用户测试的 `7447840707452882203` 返回 `filter_reason: SYSTEM_ITEM_NOT_EXIST`（视频已删除/失效），不是解析 bug。

| 方案 | 对齐架构 | 速度 | 对齐可靠 | 成本 | 加权 |
| --- | --- | --- | --- | --- | --- |
| A 复用转写结果，按字符分块送 LLM 批量翻译（JSON 数组等长回填） | 5 | 5 | 4 | 4 | **4.55** |
| B 逐句单独请求 LLM 翻译 | 5 | 2 | 5 | 1 | 3.30 |
| C 接第三方翻译 API（如 DeepL） | 2 | 4 | 5 | 3 | 3.25 |

结论：**选 A**——复用已得转写，按 ~2400 字符分块，单块以 JSON 数组送入、要求等长 JSON 数组返回，再与原文 zip 回填；长度不一致时截断/补空兜底，避免错位。译文按需触发（前端按钮），不默认消耗。

落地（继续遵循开闭原则，新增为主）：
- `backend/translator.py`（新增）：`translate_segments(segments, target_lang)`，分块批量翻译 + 长度对齐兜底，复用 `llm_client`。
- `backend/summarizer.py`（加性）：总结结果加 `transcript` 字段（全文逐句 + 秒数），供「字幕」标签直接展示与后续对照翻译复用，不再重复下载/转写。
- `backend/summary_tasks.py`（加性）：新增 `create_translate_task`，复用同一内存任务表。
- `backend/ai_routes.py`（加性）：`POST /api/translate`（基于已完成的总结任务 id + 目标语言，后台翻译）、`GET /api/translate/{id}`（进度/结果轮询）；缺 Key 503、无转写 404/409 守卫。
- 前端：`api.js` 加 `startTranslate/fetchTranslate`；`SummaryPanel.vue` 新增「字幕」标签（逐句原文 + 时间戳深链 + 语言选择 + 「对照翻译」按钮 + 进度条 + 复制），`App.vue` 加 `translation` 状态与 1.5s 轮询。

测试结论（**真实大模型，用户 Key**）：
- 连通性：`scripts/test_ai_summary.py` 含真实 LLM ping，返回「你好」，共 26 项**全 PASS**。
- 端到端（真实 LLM、合成英文转写）：英→中**总结**产出 summary/3+ 要点/带秒数章节/思维导图/transcript 字段齐全；**逐句对照翻译** 13/13 条数对齐、全部有译文、原文保留，译文质量良好（如 “Photosynthesis is how plants make their own food using sunlight.” → “光合作用是植物利用阳光制造自身养分的途径。”）。
- HTTP 全链路：路由 `/api/translate`、`/api/translate/{id}` 注册正常；后台任务生命周期 queued→transcribing→（错误时）error 经轮询正确流转与回传。
- 转写来源（真实）：YouTube 字幕命中 429、B 站字幕命中 412，均按设计优雅回退到音频+Whisper；B 站音频直链下载成功并转 16k wav（实测 3.5 分钟音频 ≈ 6.79MB）。本沙箱内 Whisper `small` 模型权重（~480MB）从 HF 镜像下载**网络阻塞**（仅缓存 2.5MB 配置/分词器、进程 CPU 近乎 0 说明在等网络），属环境/网络限制而非代码缺陷；用户本机正常联网首次下载一次后即可用。
- 前端 `npm run build` 通过（801 模块）。

经验沉淀：
- **批量翻译对齐**：逐句翻译用「JSON 数组进、等长 JSON 数组出 + 长度兜底」比逐句单请求省成本、比拼接整段更不易错位；务必显式要求「不合并/不拆分/不增删」。
- **转写一次、多处复用**：把转写结果挂在总结任务上（`result.transcript`），翻译直接读取，避免二次下载/ASR。
- **重活按需触发**：长视频逐句翻译 LLM 调用多，做成「按钮 + 独立任务 + 轮询」，默认不跑、不阻塞总结。
- **本地 Whisper 首次成本**：模型权重较大，首次需联网下载；CPU 转写较慢，可用 `WHISPER_MODEL=tiny` 降配提速；判断「卡住 vs 在算」可看进程累计 CPU（近 0 多为等网络/IO）。

## 四点二十三、修复记录：Whisper 模型下载失败 + B 站原生字幕抓取

用户实测「AI 总结」报错,暴露两个问题并修复:

**问题 1：Whisper 模型下载失败**(`An error happened while trying to locate the file on the Hub ... cannot find the requested files in the local cache`)。
- 根因:项目启动 `ensure_proxy_env` 设了 `HTTP_PROXY/HTTPS_PROXY=10808`(给海外视频站用);`faster-whisper` 经 `huggingface_hub` 下载模型时,对**国内镜像 hf-mirror** 的请求也被该海外代理路由 → 连不上。
- 修复(`backend/transcript.py` `_ensure_hf_direct`):加载 `WhisperModel` 前,把 `huggingface.co/hf-mirror.com` 等域名加入 `NO_PROXY`,让模型下载**直连镜像、绕过代理**;并对加载失败给出可读提示(建议 `WHISPER_MODEL=tiny`)。
- 验证:开着海外代理也能成功下载 `small` 模型(约 123s),后续从缓存加载、转写正常,不再报 Hub 错误。

**问题 2：B 站长视频无字幕只能 Whisper,33 分钟音频 CPU 转写极慢/易空。**
- 方案 A(加权 4.3,优于「只优化 Whisper」3.05):新增 **B 站原生字幕抓取**,有字幕秒出、无字幕再 Whisper 兜底。
- 实现(`backend/transcript.py`,全部加性):
  - `_browser_bilibili_cookies(browser)`:用 `yt_dlp.cookies.extract_cookies_from_browser` 读浏览器(Firefox/Chrome/Edge/Brave)里的 B 站 Cookie(关键是 `SESSDATA`)。
  - `fetch_bilibili_subtitles(url, browser)`:`web-interface/view` 取 `cid/aid` → `player/wbi/v2`(带登录 Cookie)取 `subtitle.subtitles` → 下载字幕 JSON(`body[].{from,to,content}`)→ 转带时间戳分段;语言优先级 人工中文>AI中文>英文。
  - `get_transcript` 接入:B 站**先试原生字幕**,失败再 yt-dlp,再 Whisper。前端早已把所选浏览器传入,无需改前端。
- 实测结论:Cookie 读取/接口/解析链路全通;但用户 Firefox **未登录 B 站(无 SESSDATA)**,匿名 `subtitles=0` → 仍回退 Whisper。**需用户在浏览器登录 B 站后**才能抓到 CC/AI 字幕(且该视频是否真有字幕,登录后才能确定)。

经验沉淀:
- **国内镜像下载务必绕过海外代理**:凡是经 `requests`/`huggingface_hub` 访问国内站(hf-mirror、B 站等),要么 `trust_env=False`,要么把域名加进 `NO_PROXY`,否则会被全局代理误路由。
- **B 站字幕强依赖登录态**:匿名拿不到 CC/AI 字幕(`subtitles=[]`);必须有 `SESSDATA`。排查时先看 cookie 里是否含 `SESSDATA`,能快速区分「没登录」与「视频真无字幕」。
- **ASR 是兜底而非首选**:长视频 CPU 转写又慢又可能空(纯音乐/VAD 滤除);能拿字幕就别转写。

## 四点二十九、迭代记录：抖音 AI 总结误走 yt-dlp 要 Cookie

现象：视频**下载**可无 Cookie，但 **AI 总结**报「抖音需要浏览器 Cookie 校验」。

根因：`transcript.get_transcript` 非 B 站时统一走 `_download_ytdlp_audio`（yt-dlp Douyin 提取器要 `s_v_web_id` 等 Cookie）；而 `downloader._download_douyin` 早已走 `douyin.py` 分享页/API + 匿名 Cookie + WAF，两条链路不一致。

开源调研（四点十二，仍成立）：Evil0ctal/Douyin_TikTok_Download_API、jiji262/douyin-downloader、JoeanAmier/TikTokDownloader、yt-dlp DouyinIE **均依赖 Cookie 或 a_bogus 签名**，没有稳定「完全无 Cookie」的通用开源方案；本项目已实现的 **iesdouyin iteminfo + 分享页 _ROUTER_DATA + WAF 解题 + platform_cookies 匿名池** 已是公开视频最优路径。

修复：`transcript.py` 新增 `_download_douyin_audio`，抖音与下载模块同源直链拉音视频再 ffmpeg 转 wav；仅 `douyin.py` 也失败时才提示 Cookie（风控升级边界）。

## 四点三十九、迭代记录：思维导图胶囊主题（方案 A）

### 背景

### 方案对比（摘要）

| 方案 | 说明 | 综合 |
|------|------|------|
| A markmap + CSS 胶囊 | 隐藏高亮条与节点底线，foreignObject 圆角底 | **8.6/10** ✓ |
| B Mind Elixir | 块状节点好看，需换渲染层 | 7/10 |
| C SimpleMindMap | 颜值最高，迁移成本大 | 6.5/10 |

### 落地

- **`mindmapTheme.js`**
  - `getMarkmapStyle(id)`：经 markmap 官方 `style` 回调注入实例级 CSS
  - 隐藏 `markmap-highlight rect` 与 `.markmap-node > line`（去掉蓝条下划线）
  - 按 `data-depth` 0/1/2/3+ 设置胶囊底：白底根节点、浅蓝一级、灰底叶子
  - `deriveOptions` 保留蓝系三色 + `colorFreezeLevel: 2`，加大 `paddingX` / `spacingVertical`
- **`SummaryPanel.vue`**：移除 JS 后处理 `applyMindmapTypography`（改由注入 CSS 持久生效）；`--markmap-highlight-node-bg: transparent`

### 经验

- markmap 的「下划线」来自节点内 `line` 元素 + `markmap-highlight rect`，只改字号颜色不够，必须两者都透明化再加 foreignObject 背景。
- 主题应走 `style(id)` 注入（随 SVG 内 `<style>` 导出），不要依赖 Vue `:deep` 覆盖 foreignObject 内 HTML。
- `color` 数组须经 `deriveOptions()` 转成函数，直接传数组会导致渲染空白（历史踩坑）。

## 四点五十一、TikTok 工作台播放失败（CDN 403 + HEVC）

### 现象

- AI 总结正常（说明 yt-dlp 能下片）

### 根因

1. **TikTok CDN 直链必须带 Cookie**，代理未转发 → 上游 **403**

### 方案（已实施）

| 步骤 | 行为 |
|------|------|
| 探测 | 带 Cookie 探测 CDN；检测 vcodec 是否 HEVC |
| 不可用 | 服务端下载 → `ensure_h264_mp4` → `/api/media/cache/{token}` 同源播放 |
| 可用且 H.264 | 仍走 `/api/media/proxy`（Cookie 写入 token headers） |
| 全失败 | embed 兜底 |

新增 `playback_cache.py`；`platform_cookies.netscape_cookie_header()`；匿名 Cookie 种子增加 tiktok.com。

## 四点五十三、性能优化：播放等待 + AI 总结变慢

### 用户现象

- 进入工作台后播放器转圈很久才开始播
- AI 总结整体很慢，长视频尤其明显

### 根因

| 环节 | 原因 |
|------|------|
| **播放** | 点击解析后顺序为：`/api/info`（yt-dlp 15–25s）→ 才触发 `/api/media/prepare`（**再次** yt-dlp）→ 播放器 mount |
| **YouTube** | 每次 extract 还带 bot 恢复重试，单次极慢 |
| **TikTok HEVC** | prepare 需**整段下载 + 转 H.264** 后才返回 cache token（7s+） |
| **AI 总结** | 无字幕时：抓字幕（又一次 yt-dlp）→ 下音频 → 云端 ASR / **本地 Whisper** |
| **画面融合** | `VISION_FUSION` 默认开启时，即使有字幕也会再下视频 + 最多 24 次 VLM 调用 |

### 方案对比

| 方案 | 做法 | 权重 |
|------|------|------|
| **A 综合优化（已实施）** | yt-dlp 内存缓存；有字幕跳过画面融合；默认关 VISION_FUSION；解析中并行 prepare；自动总结延迟 5s | **9.1/10** ✓ |
| B 仅前端并行 | 只改 HomeView 提前 prepare，不减少后端重复请求 | 6.5/10 |

### 落地

- `ytdlp_cache.py`：`YTDLP_CACHE_TTL` 默认 300s，供 `get_video_info` 与 `media_playback` 共用
- `vision_transcript.py`：`source=subtitle` 直接返回；`VISION_FUSION` 默认 `0`
- `HomeView.vue`：解析中即展示工作台并 `prepare`；自动总结延迟 5s，避免与播放抢带宽

### 验证

- YouTube：`get_video_info` ~21s 后 `resolve_url_playback` **~0s**（缓存命中）✅
- **回归（2026-06-25 晚）**：并发 `info+prepare` 时 leader 失败会把异常传给 follower → `/api/info` 400、无 VideoCard、无法下载。已改为**仅缓存成功**、失败不连坐；并**撤销**解析中提前 prepare 的前端改动。

### 仍可自行调优的环境变量

| 变量 | 建议 |
|------|------|
| `ASR_MODE=cloud` + `LLM_API_KEY` | 避免落本地 Whisper |
| `WHISPER_MODEL=tiny` | 必须用本地 ASR 时加快 |
| `VISION_FUSION=1` | 仅无旁白短视频需要画面融合时再开 |
| `YTDLP_CACHE_TTL` | 加大可减少同链重复解析 |

### 回归（四点五十三引入）

并发 `prepare` + `info` 时，旧版 `ytdlp_cache` 把 prepare 侧 yt-dlp **失败**传播给 info → `/api/info` 400 → **无 VideoCard、无法下载**；前端又在 `parsing` 期间提前 `prepare` → 长期「正在准备播放」。

**修复**：仅缓存成功结果；leader 失败不连坐 follower；回滚「解析中提前进工作台/prepare」。

## 四点六十四、付款成功未显示 Pro 修复（2026-06-28）

**现象**：Stripe 沙盒付款成功，顶栏仍显示「开通 VIP」。

**根因**（两类）：
1. **Webhook 未写入**：本地未开 `stripe listen`，或 `STRIPE_WEBHOOK_SECRET` 与 CLI 输出的 `whsec_` 不一致 → Supabase 无订阅记录。
2. **前端未刷新**：顶栏仅在 `onMounted` 拉一次状态；付款返回后若 Webhook 稍晚，或从成功页点回首页，状态不更新。

**方案对比**：

| 方案 | 说明 | 评分 |
|------|------|------|
| A 仅前端轮询/路由刷新 | 治标，Webhook 仍失败则无数据 | 6/10 |
| B 成功页 `sync-checkout` 主动拉 Stripe | 不依赖 Webhook 也能写库 | **9/10** |

**已实施**：B + 共享 `useBilling.js`（顶栏路由/切回标签页时刷新）。

- 新接口：`POST /api/billing/sync-checkout`（body: `session_id`）
- 成功页带 `?session_id=cs_...` 时自动同步

**手工补救已付款账号**：重启后端与前端后，浏览器打开付款成功 URL（含 `session_id`），或 Stripe Dashboard → Events → 重发 `checkout.session.completed`（需 `stripe listen` 运行且 whsec 正确）。

**经验**：会员状态以 **Webhook 或 sync-checkout 写库** 为准，不是 Stripe 成功页本身；本地开发必须 **三窗口**：后端 + 前端 + `stripe listen`。

## 四点六十五、Webhook 500 与自动同步补强（2026-06-29）

### 现象

`stripe listen` 窗口大量 `[200]`，但 `checkout.session.completed` 为 **`[500]`**，Supabase 无订阅 → 顶栏非 Pro。

### 根因

1. **`_handle_checkout_completed` bug**：`retrieve_checkout_session(expand=subscription)` 返回的 `subscription` 为对象，旧代码当字符串再 `retrieve` → 500。  
2. **幂等顺序 bug**：先写 `billing_webhook_events` 再处理业务，失败后 Stripe 重试被当 duplicate 跳过。  
3. **仅依赖 Webhook**：本地开发 Webhook 失败时无兜底。

### 修复

| 项 | 内容 |
| --- | --- |
| subscription 解析 | `_extract_stripe_id`，支持展开对象 |
| Webhook 幂等 | **处理成功后再** `mark_webhook_event` |
| 事件扩展 | 增加 `customer.subscription.created` 处理 |
| `GET /api/billing/status` | 非 Pro 时自动扫 Stripe 最近 Checkout 补写（30s 冷却） |
| `POST /api/billing/sync-me` | 手动触发补写 |
| 前端 | `useBilling.js` 共享状态；付款前存 `session_id`；顶栏 Pro 样式加强 |
| 脚本 | `scripts/repair_billing.py` 诊断 + 批量补写 |

### P0 验收结论

本地沙盒：**注册 → 付款 → 顶栏 Pro** 已通。第一期范围（支付 + 状态展示）**完成**；功能门禁留第二期。

## 四点六十六、AI 总结误报「解析失败」（JSON 解析）（2026-06-29）
