# SmartDiagram PPT 模块阶段工作汇报

**汇报日期：** 2026 年 8 月 10 日

**汇报主题：** PPT 生成稳定性、资料上传能力与交互性能优化
**当前状态：** 代码已在本地完成修改并通过主要 TypeScript 测试、类型检查和前端生产构建；尚未提交 Git、推送远端或部署生产环境。

---

## 一、阶段结论

本阶段围绕 SmartDiagram 的 PPT 生成体验，重点处理了四类问题：

1. 生成过程中页面卡顿、频繁滚动和预览刷新造成的交互不流畅；
2. 资料上传单文件上限只有 15 MiB，难以支持较大的 PDF、PPTX 和图片资料；
3. 用户要求生成 12 页时，模型偶尔只返回 11 页；
4. 模型调用状态刷新、上传网关和错误反馈在高延迟情况下不够稳定。

目前前三项均已完成代码层修复，其中上传上限已统一提升为默认 50 MiB，指定页数已增加“严格约束、自动重试、失败拒绝残缺结果”三层保护；生成页的高频更新也已进行批量处理和节流。

本阶段同时完成了 PPT 内容生成逻辑的专项检查。现有流程在“需求澄清—调研—大纲—单页初稿—设计稿—导出”的方法论上是合理的，但图片资产、真实联网检索、长文结构识别和原文覆盖校验仍需要在下一阶段补齐。

## 二、遇到的问题与影响

| 编号 | 问题 | 使用影响 | 原因判断 |
|---|---|---|---|
| 1 | PPT 生成过程中出现阶段性卡顿 | 模型流式输出时页面频繁刷新，切换页面、查看输出和操作编辑器不够流畅 | SSE 小片段逐条写入全局状态，SVG 预览和代码区跟随每个 token 重算；自动滚动和用量查询进一步放大主线程与网络压力 |
| 2 | 资料单文件只能上传 15 MiB | 大型 PDF、PPTX、扫描件和图片资料无法进入知识解析流程 | 前端、Renderer、Python 知识服务和 Nginx 分别存在固定限制，缺少统一配置 |
| 3 | 要求 12 页，模型偶尔只生成 11 页 | 交付页数与用户要求不一致，后续策划和设计阶段也会少一页 | 提示词只有软约束；旧逻辑会直接接受模型返回的较短数组，没有精确数量校验和重试机制 |
| 4 | 用量与进度刷新可能叠加 | 接口较慢时出现重复请求、状态延迟，间接加重页面卡顿 | 定时刷新不检查上一请求是否完成，接口也缺少前端超时保护 |
| 5 | 上传资料中的图片无法直接进入成品 PPT | 生成结果偏文字化，无法复用原始截图、产品图或照片 | 当前图片主要作为知识资料解析，没有形成“图片资产—页面引用—PPT 导出”的链路；真实检索通道也没有返回图片 |
| 6 | 长文生成可能偏离原文主线 | 示例、图片文件名或内嵌 Prompt 可能被误当成核心内容 | 原文在事实提取前只做基础空白处理，缺少正文、案例、图片说明和代码块的结构识别，也缺少大纲覆盖率门禁 |

## 三、已完成的修改

### 3.1 PPT 生成交互性能优化

已完成以下调整：

- 将高频 SSE 进度事件按阶段合并，并以 80 ms 为窗口批量写入状态，减少全局状态更新次数；
- 将流式设计代码显示调整为 150 ms 节流；
- 将 SVG 实时预览调整为 250 ms 节流，避免每个 token 都触发 SVG 解析、文本适配和重新着色；
- 对页面缩略图增加 React 记忆化，未变化的缩略图不再重复渲染；
- 自动滚动只在活动阶段发生变化时执行，并取消平滑滚动造成的持续布局计算；
- 模型输出区域仅在用户停留于底部时自动跟随，用户向上查看历史内容时不再被强制拉回底部；
- 删除设计区重复的 SVG 主题转换计算和重复 URL 更新；
- 用量查询增加 8 秒超时，并阻止上一次刷新未完成时再次发起刷新。

**预期效果：** 降低生成过程中的 React 重渲染、SVG 重算、布局滚动和重复网络请求，改善长时间生成、多页面缩略图和流式设计输出场景下的响应速度。

### 3.2 资料上传上限由 15 MiB 提升至 50 MiB

已将资料上传限制改为统一、可配置的默认 50 MiB：

- 新增共享上传限制模块，前端与 Renderer 使用同一套换算和校验规则；
- 浏览器选择文件时按 50 MiB 校验，并显示统一的 MiB 提示；
- PPT Renderer 和 Python 知识服务同步使用 50 MiB 限制；
- Nginx 请求体上限调整为 64 MiB，为 multipart 边界保留空间；
- Docker 构建和根环境变量增加 `VITE_PPT_MAX_MATERIAL_MB`；
- 支持通过环境变量向下调整上限，非法值或超过 50 的配置自动回退到 50 MiB；
- 保留压缩包条目数量与解压后体积保护，避免单纯放宽上传限制带来压缩炸弹风险。

**使用效果：** 能覆盖更多大型 PDF、PPTX、Office 文档和常见图片资料，同时确保前端、服务端和网关不会出现“某一层允许、另一层拒绝”的不一致。

### 3.3 指定页数精确生成

针对“12 页变 11 页”问题，已增加多层保护：

- 在大纲提示中明确要求返回“恰好 N 个页面元素”，并说明总页数包含封面和收尾页；
- JSON Schema 同时设置 `minItems=N` 和 `maxItems=N`；
- 第一次返回页数不足或超出时，自动重新生成一次，并明确告知模型上一次实际页数；
- 连续两次不符合要求时明确报错，不再接受残缺大纲，也不会用错误结果覆盖原有大纲；
- Gemini、OpenAI Compatible 和 Mock 三类适配器统一执行相同规则；
- 将项目页数上限统一为 16 页；
- 对“8-12 页”这类范围输入改为取上界 12，避免旧逻辑把数字拼接成异常页数。

**使用效果：** 12 页请求必须得到 12 页；模型无法满足时系统会明确失败并提示重试，而不是静默生成 11 页。

### 3.4 状态刷新与上传错误处理增强

- 防止模型用量定时刷新请求重叠；
- 保留“最新一次请求结果优先”的提交规则，避免旧请求覆盖新状态；
- 上传网关继续保留上游结构化错误、解析失败和超时状态；
- 资料上传超限在请求上游前即被拒绝，减少无效传输和服务资源占用。

## 五、生成逻辑专项检查结论

### 已具备的优势

- 流程已经按专家工作方式拆分为需求澄清、背景调研、大纲、按页检索、初稿、设计和导出；
- 有事实库、页面来源关联和策划稿，能够把内容规划与视觉设计分离；
- 大纲支持数字便利贴式调整，设计侧支持 SVG/SmartSlide 可编辑输出；
- 页数、版式、文案预算和视觉质量已有程序化约束。

### 尚未解决的内容质量问题

1. **原文结构识别不足**：图片文件名、分辨率、示例主题和内嵌 Prompt 会与正文一起进入事实提取；
2. **事实默认全部进入候选**：低置信度内容、待核验信息和错误提取可能被继续用于大纲；
3. **证据在阶段间逐步简化**：进入大纲和策划稿后，直接引文、来源位置和置信度没有完整保留；
4. **缺少内容覆盖率门禁**：系统能保证“正好 12 页”，但还不能保证原文四个核心章节全部覆盖、案例没有喧宾夺主；
5. **真实联网检索当前未启用**：运行态仍以模型通用知识整理为主，无法完全满足“真实、准确、可追溯”的资料要求；
6. **图片资产链路缺失**：上传图片和检索图片无法自动成为页面中的可引用素材。
